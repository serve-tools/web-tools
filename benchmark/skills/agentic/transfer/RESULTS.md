# Recipe transfer: results and decision

**Decision: keep the recipes experimental; do not replace the current Skills or require copying everywhere.**
The experiment found promising correctness gains in specific difficult tasks, but did not demonstrate a reliable overall reduction in uncached tokens or time.
The independent audit also uncovered material grading defects, so the corrected scores below are exploratory, not a replacement for the original frozen result.

## What we tested

We ran 240 fresh agent attempts: eight unfamiliar consumer tasks, three document/workflow conditions, five repetitions, and two allocation-order seeds.
Every condition had 80 attempts using gpt-5.6-luna at low effort, six concurrent workers, 32 actions, four public checks, and a 240-second agent deadline.
The recipes were authored without seeing the new task prompts or answers; task and grader authors did not see the recipe bundle.
The recipe condition required a copy before writing an adapter, so this tests the combined copy-and-adapt workflow.
Correctness was judged from the resulting artifact, without credit for reading or copying anything.

Before live measurement, eight golden solutions and 27 compiling, smoke-passing broken variants calibrated checks covering 36 stated requirement groups.
Nine independent recipe checks and five protocol checks also passed.
All materials and the package runtime were frozen and archived before the first measured attempt.
The completed run had exactly 240 unique planned identities, no omitted or substituted trials, no worker errors, and an unchanged host runtime.

## Why the audit changed scores

Two reviewers inspected 24 deterministically selected anonymous artifacts using only each prompt and source, with no condition labels, read history, or scores.
A separate outcome-blind semantic review confirmed two unfair grader rules: rejecting harmless extra fields on initial preference records, and requiring synchronous TypeError delivery where the task explicitly allowed operation/result rejection.
The latter also affected public repair feedback, so rescoring saved code cannot reconstruct how agents would have worked with fair feedback from the start.

Correcting those rules recovered 25 previously rejected artifacts.
New probes for positive matched web-link IDs and preservation of the existing URLPattern global then removed five passes: three docs, one current, and one recipe artifact.
All 90 affected saved artifacts were rechecked using the archived runtime; the original grades, costs, prompts, and traces remain untouched.
The probes, positive alternative implementations, and an additional broken variant were independently reviewed and passed two new regression tests.
A suggested invalid-get rejection rule was excluded because the prompt did not explicitly require it.
The polyfill import concern remains conditional: removing native URLPattern would break the required router itself, so the audit preserved the supported environment and checked for actual mutation instead.

## What the evidence supports

The original recipe-minus-current success difference was +12.5 percentage points, with a task-clustered 95% interval from −10.6 to +35.6 points.
After exploratory corrections it was +25 points, with an interval from −2.6 to +52.6 points.
This is promising, but eight task families leave substantial uncertainty and the second estimate is post hoc.
The original elapsed-time relative interval was −10.4% to +15.6%, which did not meet the predeclared no-more-than-10%-regression bound.
The uncached-savings gate could not be evaluated with complete usage; its required 15% saving was not established.
The original replacement gate failed, and material post-run grader defects independently prevent a positive adoption claim.

The strongest exploratory signals are preference-service wiring, resource cleanup, and restartable calculations.
For page loading and binary packets, every approach passed the audited checks, while the recipe workflow took longer on average.
These results concern integrations on one model, not package execution speed or all possible consumer tasks.

## Copying is not the same as reuse

All 80 recipe attempts copied a file, versus only one in the first experiment.
The median retained fraction of substantial recipe lines was only 11.5%; 32/80 retained at least half.
34/80 retained at least one manifest-named helper structurally, and 31/80 also had identifier occurrences outside that helper declaration.
These are conservative static diagnostics, not proof that a helper executed; renames and rewrites can be missed.
The blind review found substantial unused helpers in two sampled artifacts.

Copying produced an initial file after about 8.3 seconds, but the first authored adaptation arrived after about 34.6 seconds—essentially the same as current Skills at 34.4 seconds, and later than docs at 30.1 seconds.
An early pasted file therefore did not mean earlier completed work.

## What changed and what I would change next

Added eight independently tested experimental recipes, a repeatable three-condition harness, frozen-material checks, paired accounting, copy/retention diagnostics, blind review packets, and reproducible post-run corrections.
Added positive-alternative grader tests: different legitimate implementations must pass, alongside broken ones that must fail.
No production package implementation or published consumer Skill was changed by this follow-up, and nothing was published.
There is **no measured package-runtime improvement** from this work.

Keep current Skills and ordinary docs available; retain the new recipes as experimental material.
For a fresh evaluation, offer focused helpers when they fit rather than forcing a whole-file copy, add unfamiliar tasks beyond these eight families, and fix final token accounting for action-budget exits before making efficiency claims.
These changes are expected to reduce irrelevant copying and false grading, but their token/time benefit still needs measurement.
A future confirmatory run needs a new protocol and independent freeze incorporating the discovered corrections; do not relabel this post-run rescore as that run.
