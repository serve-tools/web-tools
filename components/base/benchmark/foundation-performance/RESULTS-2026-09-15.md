# Deferred binding-scope performance, September 15, 2026

Accepted: allocate BaseElement's binding scope at first layout initialization instead of in every constructor.
A never-connected element avoids the scope controller and its Set.
Normally connected elements still allocate the scope before any layout hook; binding capture, rollback, suspension, reconnection, and error semantics remain.

## Timing

Five independent counterbalanced pairs in Chromium 153.0.8010.12 on Apple M5 Max / Darwin 25.6.0 / Node 24.16.0 compare matching production bundles.
The predeclared primary metric is median batch latency; the practical threshold is 5%.
Each workload starts in a fresh page/context, with five warmup and thirty measured batches.
Construction uses 100,000 never-connected creations per batch; the earlier 10,000-element medians changed bands between processes, so this allocation-heavy diagnostic averages more natural collection cycles without forcing GC.
This is a new protocol, not a relabeling of the older construction result.

The three construction medians clear the 5% improvement threshold.
Connected lifecycle, reconnection, and update median and p95 intervals all remain above the no-material-regression boundary of `1 / 1.05`.
Each individual interval establishes the scoped 5% bound, without a simultaneous suite-wide confidence claim; they do not establish an improvement or exact equality.
The generic comparator calls them inconclusive because its verdict tests for an improvement exceeding 5%, a different question from the regression bound.

Base and Checkbox construction also clear the 5% improvement threshold at p95.
Option construction's p95 improvement interval is 4.44–8.64%, so its tail improvement does not clear that practical threshold.
All raw batches are retained; no successful run was discarded.

## Retained JavaScript heap

Five additional independent pairs explicitly collect garbage before measurement, after retaining 10,000 never-connected elements, and after releasing those references.
GC never runs in the timed suite.
The following values are median retained JavaScript heap increases over each page's initial collected heap:

| Component | Before bytes | After bytes |      Delta |
| --------- | -----------: | ----------: | ---------: |
| base      |    1,811,368 |     560,480 | -1,250,888 |
| option    |    3,147,972 |   1,899,068 | -1,248,904 |
| checkbox  |   12,386,124 |  11,129,636 | -1,256,488 |

The savings are approximately 1.25 MB per 10,000 never-connected elements, or approximately 125 bytes per element in this diagnostic.
These are JavaScript heap values, excluding native DOM/browser memory; they do not establish total memory savings or leak freedom.
Released residuals were approximately 0 KB for Base, 5–6 KB for Option, and 174–176 KB for Checkbox, with no increase in the candidate; runtime caches are not assumed to disappear when the fixture does.

## Size and contract

The standalone library changes from 202,993 to 202,994 raw minified bytes: **+1 byte**.
The component-only library stays at **184,233 bytes**, with generic foundations excluded.
Public entrypoints and runtime dependencies are unchanged.
The candidate initializes its scope before creating the detached fragment or invoking subclass hooks, retains the same scope on retry, and tolerates disconnection before any scope exists.
